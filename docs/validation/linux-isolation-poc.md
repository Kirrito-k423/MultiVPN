# Linux 原厂客户端隔离 PoC 验证

日期：2026-10-08，更新于 2026-10-09（北京时间）。分支：`codex/linux-isolation-poc`。关联 [Issue #7](https://github.com/Kirrito-k423/MultiVPN/issues/7)。

本记录只发布匿名结果；原厂包、网关、目标地址、账户、凭据和原始记录保留本机忽略目录。

## 环境及软件来源

- 宿主：macOS 15.7.4，Apple silicon，16 GiB 内存；现有原生 UniVPN 连接保留。
- 原厂 Linux ARM 客户端：10781.21.0.0831；`.run` 实际架构为 aarch64，其 MD5 与[原厂下载页](https://www.leagsoft.com/doc/article/103197.html)一致。MD5 对应安装文件，不是包含证书文件的外层 ZIP；发布页校验与 TLS 下载结合记录，不把 MD5 单独视为密码学来源证明。
- 初始启动检查：现有 Debian 13 ARM 容器里原厂 CLI 能显示配置菜单；这个结果只证明启动，不证明原厂支持 Debian 或 VPN 可用。
- 标准环境：固定 digest 的官方 Ubuntu 26.04 ARM64 镜像，来源为[Ubuntu 官方镜像渠道](https://ubuntu.com/docs/oci-registries/oci-how-to/getting-started/)。已在此基础构建并启动两套原厂客户端环境。

## 结果与边界

| 检查 | 当前结果 | 证明范围 |
|---|---|---|
| 原厂包版本、架构及安装文件校验 | 通过 | 取得匹配架构的原厂安装文件 |
| 原厂 Linux CLI 进入配置菜单 | 两个 Ubuntu 容器同时通过 | 未认证的客户端可启动 |
| 目标/安装包校验、目标策略快照、所有权限制、loopback、管理身份变化拒绝、普通网卡拒绝放行、规则不经 flush、允许规则绑定 TUN | 10 项模型控制测试通过 | 控制逻辑，不是内核或 VPN 证明 |
| 两个 Ubuntu 容器的进程、网络、后台端口和管理身份隔离 | 通过初始运行检查 | 各自运行原厂后台/CLI；管理身份不同，未经过 VPN 路由变化 |
| 宿主到 guest 的 SSH 公钥登录和固定主机身份 | 两个 guest 均通过 | 管理通道在拨号前可用，不代表拨号后可用 |
| 未认证时的真实目标访问拒绝 | 两个 guest 均通过 | 指定目标请求立即被拒绝；普通网卡的 `allow` 请求被拒绝 |
| 原厂配置持久化 | SSH 登录会话通过 | `docker exec` 会话保存失败；真实登录会话已保存配置 |
| 停止一个未认证 guest | 另一 guest 管理 SSH 与宿主原生 VPN 的已知目标仍可访问 | 仅证明当前管理与宿主路径隔离，不代替两个已认证 VPN 的独立断线测试 |
| 第二个网关的原厂认证 | 用户更正密码后成功，建立 TUN 接口和内网路由 | 该网关的 SSL 用户名/密码流程，不代表其他认证方式 |
| 原生 VPN 与 guest VPN 同时访问各自目标 | Mac ARM 实测通过：宿主一个 SSH 目标与 guest 两个 SSH 目标并行成功 | 服务身份使用已有主机密钥校验；不是两套 Linux guest 双认证或其他平台证明 |
| 断开 guest 后宿主原 VPN 仍可用 | 一次断开测试通过，宿主新 SSH 请求与 guest 管理入口仍正常；重连后恢复双路径 | 只验证 guest 断开这一方向，未中断宿主原生 VPN |
| 管理终端关闭后 VPN 保持 | tmux 会话退附、SSH 退出后，guest 的两个目标与宿主目标仍并行成功 | guest 内保留原厂终端；不支持容器重启后自动认证 |
| 真实出口/DNS、IPv6/UDP、全隧道、重建竞态 | 未验证 | 不满足完整 R5/R6 验收 |
| Windows x64 / Mac Intel 原厂运行 | 未验证 | 共享脚本测试不代表真实兼容性 |

目前形成了 Mac ARM 上“宿主原生 VPN + 一个 Linux guest VPN”的真实并行 SSH 证据；没有完成全部需求或发布可用桌面安装包。

## 2026-10-09 认证复查

第一轮用户提供的密码有误，原厂日志记录认证请求发送成功、网关回复拒绝码 `196609`（`0x30001`），没有建立隧道。用户更正密码后，新的认证返回 `Successful login` 与 `Succeeded in enabling network extension`，实际建立了 TUN 接口和内网路由。密码输入时终端回显关闭，未开启记住密码；没有猜测密码或自动重试。

认证前的证书获取曾记录验证失败；随后原厂 CLI 按其现有行为完成 TLS 连接并发送认证请求。本次没有修改原厂证书设置，也没有出现供确认的证书提示。因此不能把证书获取失败直接归因为这次认证被拒绝的原因，也不能据此认定网关身份验证已合格。

原生客户端配置已通过原厂导出功能保存到本机私有目录，确认网关、端口和连接模式与 guest 一致；导出不包含账号或密码。认证尝试后，宿主原生 VPN 的已知 SSH 目标仍可免密访问。Windows x64、Mac ARM 和 Mac Intel 的现有 CI 均通过，但这些检查不包含真实 VPN 认证。

## 真实并行访问、断开与恢复

- guest 四个指定 SSH 目标均响应：两个目标使用 Mac 已有的 Ed25519 主机密钥及用户公钥完成免密登录；一个目标的 Ed25519 和 RSA 主机密钥均与已有记录不同，保持拒绝登录；另一个目标通过主机身份校验但拒绝当前用户公钥。没有自动替换服务器身份记录或更改服务器权限。
- 对两个可登录 guest 目标及一个宿主原生 VPN 目标并行建立新 SSH 请求，均返回预期命令标记。guest 的允许规则绑定实际 TUN 接口，管理 SSH 在 VPN 路由下仍可访问。
- 在原厂 CLI 中使用 `q` 断开 guest VPN，宿主原生 VPN 的新 SSH 请求和 guest 管理 SSH 继续成功。两个原先可登录目标的 TCP 22 请求立即返回连接拒绝，守卫钩子与拒绝规则仍在，未走普通网卡回退。这是两个已知 IPv4/TCP 目标的一次断线样例，不是完整 R6 或竞态验证。
- 更正后的认证再次成功。新增 guest 内 tmux 会话保留原厂终端；退附后管理 SSH 已退出，原厂进程仍运行，三个目标的新请求仍并行成功。更新后的 Dockerfile 已从已校验原厂包重新构建，并在独立未认证 guest 中实测 CLI 启动与 tmux 退附，随后停止该测试 guest。
- 第一次断开后，guest 的解析配置仍保留原厂添加的 DNS 条目，`host.docker.internal` 解析失败；未修改宿主 DNS。DNS 恢复、内网域名归属及浏览器、IPv6/UDP 尚未验收，不把 SSH 成功推导为这些能力已可用。
